# AGENTS.md

## Purpose
commitsmith — a pnpm-based Node.js CLI (`node commitsmith.mjs`) that generates conventional-commit
messages for staged git changes, using a local (Ollama) or cloud (Ollama Cloud, OpenAI, Anthropic)
provider. Entry point `commitsmith.mjs` is a thin wrapper; all logic lives under `src/`
(`src/cli.mjs` dispatches, `src/modes/*` are the run modes).

## Key Commands
- `npm test` — syntax check (`scripts/check-syntax.mjs` runs `node --check` on `commitsmith.mjs` + every `src/**/*.mjs`) then unit tests (`node --test "test/**/*.test.mjs"`). `test:syntax` / `test:unit` split the halves.
- Run the tool: `node commitsmith.mjs` — default is one commit for everything staged; flags: `--split` (per-file), `--split-hunks` (per-`@@` hunk), `--group` (model clusters files), `--commit`/`-y` to commit, `--check`, `--dry-run` (split-hunks only — it's ignored elsewhere, per a warning in `cli.mjs`).
- `node commitsmith.mjs init` / `use` — interactive setup / quick provider switch; package.json aliases exist too: `commit`, `commit:go`, `commit:split`, `commit:hunks`, `commit:group`, `commit:check`.
- If nothing is staged, the CLI prompts to stage files (`modes/interactive-stage.mjs`) — on a bare `commitsmith` run it also asks which mode and commit behavior (ask/auto/preview) to use.
- `node commitsmith.mjs --release-notes [--from <ref>] [--branch <ref>] [--max-chars <n>] [--copy]` — print user-facing release notes (bullets on stdout, header/progress on stderr) for the changes since the last git tag reachable from the target (or `--from <ref>`), target = HEAD or `--branch <ref>`; read-only, for pasting into store consoles (Play Store, App Store). Package.json alias: `release-notes`.

## Modes
- Single (default) — one commit for all staged changes. Split — merges related files into one commit each, strict per-file otherwise (`--no-group-detection` forces strict).
- Split-Hunks — resets the index and applies each hunk with `git apply --cached` (via `execFileSync` arrays — never interpolate file paths into shell strings).
- Group — sends all staged diffs in one request; missing/duplicate files swept into a trailing `chore: update …` commit; falls back to Split on an unparseable response.
- Breaking (`--breaking [--from <ref> [--branch <ref>]]`) — read-only dry run: asks the model (`buildBreakingPrompt`) only whether the staged/unstaged/range diff has breaking changes, prints findings + a `BREAKING CHANGE:` footer; exit 1 = breaking, 2 = unparseable answer. `prepareBreakingInput()` validates before the provider check; big diffs are analyzed per file. `--check --from <ref>` scans every commit in a range for unflagged breaking changes.
- Pull request (`--pr [--base <branch>] [--create|-y] [--draft]`) — `preparePullRequest()` (git only, runs before the provider check) → `runPullRequestMode()` in `src/modes/pull-request.mjs`: PR title/body from `getReleaseCommits` + `getBranchDiff` via `buildPullRequestPrompt`; breaking notes come from commit footers (`collectBreakingNotes`). Preview unless `--create`/`-y`; creating shells out to `gh` via `src/github.mjs` (body on stdin, array args), pushes with `pushBranch` (never forces). `preparePullRequest()` also calls `findOpenPr()` (the one network call in prepare; null if `gh` is missing): an open PR is updated with `gh pr edit` (`updatePullRequest`) instead of duplicated. `--as-bot` / `COMMITSMITH_PR_AS_BOT` / config `prAsBot`: `resolveBotToken()` in `src/github-auth.mjs` returns `COMMITSMITH_GH_TOKEN` or exchanges a GitHub App JWT (`COMMITSMITH_GH_APP_ID` + `_KEY_PATH`, optional `_INSTALLATION_ID`) for an installation token; it is passed to `gh` only via `GH_TOKEN` in the child env (`ghEnv`), never argv/disk/logs, and `checkGh(token)` skips `gh auth status` for it. `commitsmith init github` (`src/modes/init-github.mjs`) is the guided setup: verifies App ID + key via `verifyBotSetup()`, optionally copies the `.pem` to `<config dir>/github-app.pem`, and merges `githubAppId` / `githubAppKeyPath` / `githubAppInstallationId` / `prAsBot` into the global config (key path always global) or the project `.commitsmithrc.json` via `mergeConfigFile()`. Because cosmiconfig returns only the first config file found, `loadConfig()` reads these keys from the global file as a fallback (`GITHUB_BOT`). `gh` calls are not unit-tested; `buildPrCreateArgs`/`buildPrEditArgs`/`parseOpenPr` and the parsers are.
- Release Notes — prints user-facing bullets since the last tag (or `--from <ref>`), compared against HEAD or `--branch <ref>`; `prepareReleaseNotes()` validates refs *before* the provider check (see `cli.mjs`); input = commit list (`getReleaseCommits`) + filtered three-dot diff (`getReleaseNotesDiff`); base via `getBaseTag()` in `src/git.mjs`; prompt `buildReleaseNotesPrompt({commitsText, diff, context, maxChars})`; `COMMITSMITH_RELEASE_NOTES_CONTEXT` / `releaseNotesContext` config key.

## Configuration
Precedence: **env var > config file > OS keychain (API key only) > built-in default**.
- `loadConfig()` in `src/config.mjs` is async + memoized — nothing reads the config file or keychain until the first call, so importing `config.mjs` has no side effects.
- Config file keys are camelCase: `provider`, `apiKey`, `model`, `host`, `maxDiff` (6000), `timeoutMs` (60000), `groupMaxDiffPerFile` (1200), `fallbackModels`, `breakingDetection`.
- Env vars: `COMMITSMITH_PROVIDER`, `COMMITSMITH_MODEL`, `COMMITSMITH_HOST`, `COMMITSMITH_API_KEY`, `COMMITSMITH_MAX_DIFF`, `COMMITSMITH_TIMEOUT_MS`, `COMMITSMITH_GROUP_MAX_DIFF_PER_FILE`, `COMMITSMITH_FALLBACK_MODELS`.
- Per-provider model/host defaults (`DEFAULT_MODELS` / `DEFAULT_HOSTS`) live in `src/config.mjs`.

## Release & CI (as the workflows are today)
- Push anywhere → `.github/workflows/ci-check.yml` ("CI", Node 22 & 24): `pnpm install --frozen-lockfile`, `pnpm test`, a `node commitsmith.mjs --help` smoke test, `package.json` validation, `pnpm audit --production`, `pnpm pack`. All must pass.
- User-facing CI documentation lives in `docs/ci.md` (command cheat sheet, exit codes, PR checks, release options); update it when a CI-relevant command, exit code or action input changes.
- After CI succeeds on `main` → `bump-version.yml`: uses `masgeek/github-tag-action@release` (the maintainer's fork; branch `release` carries compiled `lib/`) with `tag_prefix: ""`, `create_annotated_tag`, `default_bump: "false"`, `gitmoji`, `extended_release_rules` and `create_release`, authenticated with the GitHub App token. The fork parses gitmoji conventional commits itself (breaking → major; docs/test/ci/chore only → no release), so the version depends on commit-message quality (a wrongly flagged 💥 commit means a major bump); fix with `--amend`/`--reword` before merging. Changing the rules means changing and re-publishing the fork's `release` branch, not this repo. `commitsmith --bump` and `release/action.yml` implement the same rules for local use and other projects, and are not used by this repo's workflow.
- On a release being published → `publish-npm.yml`: pins `package.json` version to the tag, runs `pnpm test` + `--help` smoke, then `npm stage publish --provenance --access public`; a human must run `npm stage approve` (or npmjs.com with 2FA) before it goes live — the Trusted Publisher is configured stage-only on purpose. First-ever npm publish is manual.
- `next-release.yml`: when CI succeeds on the `develop` branch, it opens a PR titled "Release: <first line of commit message>" targeting `main`.

## Gotchas Agents Might Miss
- **Help is data, not a text blob:** `src/help.mjs` holds a `TOPICS` registry (one entry per command: group, label, summary, usage, options, examples, notes, see). `commitsmith --help` renders a one-line-per-command overview; `help <topic>`, `<command> --help` and `--flag --help` render one page (`resolveHelp`, `FLAG_TOPICS`, `ALIASES`). **When you add a command or flag, add/extend its `TOPICS` entry** (and a `FLAG_TOPICS` mapping for a new mode flag); `test/help.test.mjs` fails if a topic is incomplete, mis-linked or missing from the overview. Don't put per-command detail in the overview.
- **Offline modes** (`--scan`, `--bump`, `--changelog`, `--lint-message <file>`, `hook …`) are dispatched in `cli.mjs` *before* `loadConfig()` on purpose: git hooks run them on every commit, so they must not touch the config file, keychain or provider. Don't add a `loadConfig()` call to their paths. Pure logic lives in `src/conventional.mjs` (header parsing, `computeBump`, `bumpVersion`, changelog formatting/insertion, `lintCommitMessage`) and `src/secret-guard.mjs`; both are covered by `test/guards.test.mjs`. `--bump` base = last tag reachable from the target (no fallback to the previous tag, unlike release notes). `--changelog` is full-history: `listVersionTags()` (`git for-each-ref --merged`, semver tags only) → `buildChangelogSections()` (unreleased first, then each tag over `buildReleaseRanges`) → `renderChangelog` for stdout/new files or `mergeChangelogSections()` for an existing `--output` file (refreshes Unreleased, inserts missing releases in version order, never rewrites a release already in the file; `--rebuild` bypasses the merge); `setPackageVersion` edits only the top-level `version`. Hooks (`src/modes/hook.mjs`) carry a `HOOK_MARKER` and only ever touch files containing it; `--force` backs up a foreign hook as `<name>.commitsmith-backup`.
- **Rules / tickets / gitmoji:** `commitRules` is normalized by `normalizeRules()` (`src/rules.mjs`, never throws — bad values become warnings shown by `doctor`) and reaches `loadConfig()` as `RULES`/`RULE_WARNINGS`; the offline `--lint-message` path uses `loadRulesFromFiles()` instead (config *files* only — no keychain, no provider; config.mjs imports rules.mjs, so rules.mjs must not import config.mjs). Rules flow through `getEffectiveRules()` (`src/generate.mjs`, applies `--no-gitmoji`) into `buildPrompt`/`buildGroupingPrompt` (`ruleLines`), `formatCommitMessage(parsed, breaking, rules)` and `parseGroupingResult(..., rules)`. Anything that parses a message header must use `parseCommitHeader` (emoji optional); `isBreakingMessage` also accepts `type!:` and a `BREAKING CHANGE:` footer. Ticket footers (`src/tickets.mjs`: `extractTicket`, `appendFooter`, `withTicketFooter`) are added by `addTicketFooter()` in generate.mjs/group.mjs and as `footer` in the PR body. Project config *replaces* global config (cosmiconfig returns the first file), so `commitRules`, ticket keys and the GitHub App keys explicitly fall back to the global file in `loadConfig()`.
- **`--amend`** (`src/modes/amend.mjs`) rewrites only the message: it dies when anything is staged, and for an already-published HEAD requires the menu confirmation or `--force` with `-y`. **`--review`** reuses `prepareBreakingInput({ flag, rangeDiff })` and the per-file strategy of `--breaking`; `--fail-on` sets the exit code. **`doctor`** is dispatched right after `loadConfig()` (it works outside a repo) and uses `probeProvider()` (non-exiting twin of `assertProviderReachable`); `checkNodeVersion`/`summarizeChecks` are unit-tested in `test/features.test.mjs`.
- **Secret guard:** `callModel()` (`src/providers/index.mjs`) runs every prompt through `guardPrompt()` (`COMMITSMITH_SECRET_GUARD` = redact|block|off, `--no-secret-guard`). New model calls must go through `callModel` so they are covered. Redaction is pattern-based, not a guarantee; test secrets must be assembled at runtime so the repo never contains a real-looking token.
- Generated commit messages get a second breaking-change pass: `addBreakingFooterIfNeeded()` in `src/generate.mjs` (also called per group in `src/modes/group.mjs`) runs `buildBreakingPrompt` on messages not already marked 💥 and adds the `BREAKING CHANGE:` footer via `retypeMessage`. It adds one model call per message, is skipped when `breakingDetectionEnabled` is false, and is not unit-tested (needs a model); the pure parts (`parseBreakingResult`, `retypeMessage`, `breakingReason`) are.
- Interactivity is gated by `isInteractive()` in `src/tty.mjs` (TTY on stdin+stdout, `CI` unset, no `--no-interactive`). Never call clack from a path that can run non-interactively; `confirmWithEdit` (`src/ui.mjs`) declines instead of prompting. Remembered choices live in `src/prefs.mjs` (`state.json`, separate from config). Pure helpers (`moveFile`/`mergeGroups`, `planHunkBatches`, `retypeMessage`, `computeInteractive`) are covered by `test/interactive.test.mjs`; the clack flows themselves are not.
- `test/git.test.mjs` covers `parseFileDiffIntoHunks` / `extractPathFromFileDiff`; `test/parsing.test.mjs` covers `parseModelJson` / `formatCommitMessage` / `fallbackFromRawText` / `parseGroupingResult`. Green `npm test` = parsing and hunk logic didn't regress, not "the CLI works end to end."
- `src/cli-args.mjs` mode/commit flags (`shouldCommit`, `autoYes`, `splitMode`, `splitHunksMode`, `groupMode`, `dryRun`) are mutable live ESM bindings — `setRunOptions()` changes them after the fact in interactive mode.
- `--no-breaking-detection` disables the 💥 breaking-change classification (default on); config-file key `breakingDetection: false` does the same.
- All git shell-out goes through `execFileSync` with argument arrays (`src/git.mjs`, `src/modes/split-hunks.mjs`).
- Model must return **pure JSON**; `formatCommitMessage` falls back to the first line (`fallbackFromRawText`) if not.
- **Workflow modes:** `--fixup` and `--lint-commits` are dispatched in the offline block of `cli.mjs` (no `loadConfig()`; `--lint-commits` reads rules via `loadRulesFromFiles()`); `--release` runs right after `loadConfig()` and before the provider check (it needs only git + optional `gh`/bot token); `--reword` and `--standup` run after the provider check. `--release` (`src/modes/release.mjs`) reuses `resolveRelease()` + `buildChangelogSections()`/`mergeChangelogSections()` (the unreleased section labelled with the new version; its body is the GitHub Release text), refuses uncommitted changes, previews unless `-y`/confirm, and `--github` requires `--push` (`gh release create --verify-tag`, notes on stdin). `--reword` re-creates commits with `git commit-tree` on the same trees/authors/dates (no rebase), checks the branch ref with `update-ref` compare-and-swap, and saves `refs/commitsmith/backup/…`; it requires a linear chain and `--force` for published commits. `--fixup` only offers commits newer than the upstream/default branch *and* the last tag (`sharedBase()`); blame/hunk parsing (`parseHunkRanges`, `parseBlameShas`, `rankCandidates`) is pure and tested. All of these are covered by `test/workflow.test.mjs`; the git/gh/model parts are not.
- **Prompt hints:** `getEffectiveRules({ files })` (`src/generate.mjs`) adds `styleExamples` (recent conventional subjects, config `styleExamples`, `--no-style`) and `scopeHint` (`inferScope()` in `src/hints.mjs`, config `inferScope`, `--no-scope-hint`) to the rules object; `ruleLines()` renders them, so `buildPrompt`/`buildGroupingPrompt` need no extra parameters. An empty model scope is filled from `scopeHint`. `analyzeStaged()` (`src/staged-check.mjs`) prints advisory size/mix warnings in single mode only (`diffWarnings`, `--no-warnings`).
- **`--release-tags`** (`src/modes/release-tags.mjs`) runs next to `--release` (after `loadConfig()`, no model): `planReleases()` (pure, tested) picks the newest tag without a release, or all of them oldest-first with `--all`; existing releases come from `gh release list --json tagName` (`listReleaseTags`), pushed tags from `git ls-remote` (`listRemoteTags`); bodies are the tag's `buildChangelogSections()` section via `releaseBody()`. `--bump --tag --push` pushes only the tag (`pushRefs(['refs/tags/<tag>'])`); adding `--github` first runs `resolveGhToken()` (gh + bot token, before anything changes) and, after the push, `publishTagRelease()`. That is the one place `--bump` (an offline-block mode) touches `loadConfig()` — only when `--github` is passed, never from hooks.
- **Release action:** `release/action.yml` is a reusable composite action (`masgeek/commitsmith/release@…`): `--bump --json` → `--changelog --unreleased --stdout --release-version <tag>` → annotated tag push (the checkout's credential header is replaced by the `token` input) → `gh release create --verify-tag`, deleting the tag again if that fails. Inputs/outputs are documented in the README; `cli` overrides the npm package (this repo's `bump-version.yml` passes `node commitsmith.mjs` so it releases the code CI just tested). Inputs reach the shell only through `env:`. The decide/notes steps are worth re-running locally after changing `--bump --json` or the changelog output format, since the action parses both.
- **GitHub Action:** `action.yml` (repo root) is a composite action that runs `npx @masgeek/commitsmith --lint-commits --from <base>` (and optionally `--breaking --from`); user inputs reach the shell only via `env:`, never interpolated into the script.
- `npm pack --dry-run` locally is a cheap check for the `files` list and `bin` entry before any release.
